01 System architecture

System Architect view. One hardware/software base. Many automotive products. No implementation in this phase.

ESP32-C3 is a prototype edge node: one TWAI (CAN 2.0) controller, BLE 5 (NimBLE), no native dual-CAN. A second bus, if required later, is an SPI CAN controller (for example MCP2515) behind the same hal_can contract.

4. Application architecture

Each product is a single app_main that:

  1. Initializes BSP and selected HAL instances
  2. Creates the FreeRTOS task set required by that product (subset of the platform task catalog)
  3. Registers protocol and service callbacks
  4. Enters the product state machine

Feature flags such as CONFIG_PRODUCT_BLE_CAN_GATEWAY exclude unused tasks and stacks at compile time. ESP32-C3 SRAM does not allow every task in every product.

5. Middleware architecture

Middleware owns how tasks talk, not what a CAN signal means.

  • Typed message envelope: source, dest, type, timestamp, payload pointer + length
  • Static pools — no malloc on the data path
  • Logger is a sink, never a control path
  • Config is schema-versioned; invalid schema falls back to factory defaults

6. Driver architecture

Drivers implement HAL. They may use IDF. They expose:

  • Init / deinit with explicit error codes
  • ISR → queue or task notification only
  • Thread-safe TX from tasks; RX from one owner task
  • Test hooks: inject frame, force bus-off, force timeout (compile-time CONFIG_AE_TEST_HOOKS)

7. FreeRTOS and inter-task communication

See 04 Task architecture for the full catalog. Rule: ISR never parses UDS or BLE ATT. ISR never logs strings.

8. Error, logging, configuration, diagnostics

Error handling

Every public function returns ae_status_t (0 = OK). Codes are (module << 8) | reason. Callers do not ignore returns. Fault manager consumes repeated errors.

Logging

Compile-time levels. ISR uses a lock-free drop-counter, not printf. Task logger drains a ring to UART. Tags: CAN, BLE, UDS, OS, HAL, APP.

Configuration

Static Kconfig + a small NVS blob (bitrate, BLE name, route table version). Dynamic writes require diagnostic session + security access prototype.

Diagnostics

DTC manager is a service. UDS, OBD, BLE, and UART are transports that publish the same DTC table.

10. Constraints that shape the design

  • ESP32-C3 SRAM is limited — subset tasks per product
  • One native CAN controller — dual-bus is a later HAL instance, not a second stack
  • BLE and TWAI together must be measured (Phase 17 performance)
  • This is a production-quality prototype, not a certified ECU
