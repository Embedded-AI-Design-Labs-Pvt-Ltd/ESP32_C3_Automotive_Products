08 Repository structure

Live code stays in platform/, products/, and ports/. Logical playbook names are mapped in directory_structure.md — no big-bang rename.

ESP32_C3_Automotive_Products/
├── CMakeLists.txt                 POSIX host tests (no ESP32 required)
├── osal/                          POSIX + FreeRTOS backends (phase A2)
├── apps/                          thin CLI entrypoints (later)
├── cloud/  dashboard/  configs/   later; no secrets in git
├── docs/                          HTML portal + docs/architecture/*.md
├── platform/                      reusable C (HAL host impl exists)
├── products/                      P01–P17 compositions
├── ports/                         virtual_ecu, arduino, esp32_c3, rpi5
├── tests/unit/                    host tests (integration/HIL later)
├── tools/gui/                     Virtual ECU GUI
└── .cursor/                       agents + rules

ESP-IDF project (planned, Phase 3)

ports/esp32_c3/
  CMakeLists.txt
  sdkconfig.defaults
  main/                 product-selected app_main
  components/           or EXTRA_COMPONENT_DIRS=../../../platform

Platform folders become IDF components. Products select one main.

Include rules

FromMay includeMust not include
Applicationservices, protocols (public), middlewareESP-IDF, driver internals
Servicesprotocols, middleware, commondrivers, IDF
Protocolscommon, framework, HAL typesIDF, product headers
Middlewarecommon, HAL, FreeRTOSUDS, product
DriversHAL, IDF, BSPUDS, BLE app logic

File naming

C: can_driver.c/.h, can_service.c/.h, isotp.c/.h, uds_server.c/.h, uds_client.c/.h. Prefix public APIs with ae_ or module name as in document 07.
