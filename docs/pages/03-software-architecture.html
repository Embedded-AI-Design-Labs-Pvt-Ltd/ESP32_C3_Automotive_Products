03 Software architecture

Module map, language split, and how products are composed without forking the stack.

1. Language policy

LayerLanguageWhy
HAL, drivers, protocols, services, firmware appC11MISRA-inspired review, stable ABI, no hidden constructors, ISR-safe
Framework patternsC11Ring buffer, SM, callbacks as function pointers
PC GUI, Virtual ECU, test harnessC++17 (restricted)Host OS, sockets, UI; no exceptions on shared protocol logic if later reused
CI / Terraform / JenkinsGroovy, HCL, shellInfrastructure, not firmware

C++ features not used on the MCU: exceptions, RTTI, iostream, dynamic new on hot paths, STL containers in ISR context.

3. C framework demonstrations (planned in Phase 4)

Phase 4 implements the patterns, not products. Each pattern gets a function banner, block comment, and line comments as requested.

  • volatile variable and volatile pointer (hardware register views)
  • const pointer and pointer to const (TX tables vs RX buffers)
  • function pointer + callback registry
  • static ring buffer (ISR put / task get)
  • intrusive singly-linked list only for deferred work items in a static pool
  • explicit memory ownership in every header

No runtime “load all 17 products.” SRAM and flash cannot host that.

5. State machines

Every protocol and service uses the framework SM:

  • Named states as enums
  • Entry / exit / tick / event handlers
  • Timeouts as SM events, not busy-waits
  • System-call style: tasks block on queues; SM runs in the owning task

Control-flow diagrams: document 06.

6. IPC model

Tasks communicate with typed messages, not shared mutable structs without a mutex.

7. Coding standard (firmware)

  • Function banner: name, purpose, thread context, ISR-safe?, ownership of buffers
  • No implicit bool for errors
  • Fixed-width types from stdint.h
  • Public symbols prefixed ae_
  • One compilation unit owns each static buffer
