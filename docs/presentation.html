AEGW-C3 · Phase 2

Automotive ESP32-C3
Edge Gateway & ECU Platform

One reusable platform. Many products. Architecture first — implementation after approval.

What we found

  • Repository was empty — greenfield.
  • No ESP-IDF project, no firmware, no prior docs.
  • This package is the first baseline.

The rule that matters

Do not build 17 separate projects.

Build one core: HAL, drivers, CAN, BLE, ISO-TP, UDS, diagnostics, logging, security, OTA, tests.

Compose products on top.

Layers

Application — product composition
Services — DTC, gateway, fault, OTA
Protocols — CAN, ISO-TP, UDS, OBD
Middleware — IPC, log, config, health
HAL → Drivers → ESP32-C3

Products (same base)

Gateway · OBD · UDS tester · Logger · Analyzer · Test box · Simulator · Fault box · EOL · Calibration · Sensor / TPMS / EV GW · IDS · HIL · Training · OTA

Real-time shape

  • ISR only queues or notifies.
  • CAN RX is the highest comms task.
  • No malloc on the frame path.
  • Watchdog never takes a mutex.

Ports and tools

  • Primary: ESP32-C3 + ESP-IDF.
  • Virtual ECU + GUI — with or without hardware.
  • Later: Arduino, Raspberry Pi 5.
  • Later: Docker, Jenkins, Terraform artifact stores.

CAN IDs

Prototype / simulated only: BCM 0x1A0, VCU 0x200, BMS 0x300, IC 0x400, diag 0x7E0/0x7E8.

Not OEM production identifiers.

Where we stop

Phase 1–2 complete. No firmware until you approve the ten documents.

Next after approval: Phase 3 BSP/HAL, then framework, then tasks, then CAN.
